# Pinned FWA tuple and token-identity continuation

**Scope and result.** At mainnet block **26,382,349**, the focused fork probe exercised three of the four tuple uses flagged in `audit/gate/detector-triage.md`: `_sync` acquisition fields, `recoverCuratedNFT`, and `_withdrawAndRedeem`. It used two curated collections with the **same token ID 1**, distinct FWA listing IDs, and two real Shapes. The selected frozen curated NFT remained quarantined, was refunded, and was returned to the creator without moving the other collection's token ID 1. Two Shape listings were later withdrawn and redeemed for exactly **0.02 ETH** backing. A separate two-request, out-of-order VRF case tried to make ordinary Shape delivery fail through caller-supplied settlement gas. Calls requesting 200,000 through 800,000 gas in 10,000 increments reverted; the first successful request, **810,000 gas**, fulfilled and delivered the Shape. It did not create a `DeliveryRefunded` Shape. These results bound the tested states; they do not establish full source-to-runtime equivalence or make the fourth path universally unreachable.

## Source identity chain

The inspected [Blockscout StandardPoolBuyback source](https://eth.blockscout.com/address/0x85Faf92967705dc45535eBCA74D6333F6bCBfEe7?tab=contract) is stored as `audit/integrations/fwa-pool-source.json`, with inherited `src/poolsV2/StandardPool.sol`. Blockscout marks it **partially verified**. Its pinned implementation runtime code hash `0x0af01fc1a6ea7ea81fd81004fdb3bd5483872df384d2e4ab4a7599e0d2f0ce02` was separately matched in `assessment.md`, but this continuation did not independently recompile source to bytecode. The [Shapes source](https://eth.blockscout.com/address/0x6fE9193276bF7aBCbEE44AB7aFd717d637D6FAf0?tab=contract), `src/Shapes.sol`, was reread via the [public Blockscout API](https://eth.blockscout.com/api/v2/smart-contracts/0x6fE9193276bF7aBCbEE44AB7aFd717d637D6FAf0); it too is partially verified.

1. **Listing key and tuple.** `StandardPool.sol` 91–106 defines `(collection,depositor,purchaser,tokenId,weight,price,slot,status)`. `_listNFT` at 751–803 rejects an already live `(collection,tokenId)`, pulls that exact NFT, checks `ownerOf`, assigns `nextListingId++`, stores the collection/token/depositor tuple and indexes `liveNFTListing[collection][tokenId] = listingId`. The source has one whole-listing assignment (line 778); later direct writes change status, purchaser, price, weight or slot, not collection/depositor/tokenId. Thus equal numeric token IDs in distinct collections do not alias the source's NFT controller.
2. **Acquisition tuple and `_sync`.** `StandardPool.sol` 108–115 defines `(purchaser,requestBlock,priceEscrowed,listingId,status,tokenPayment)`. `_openAcquisition` at 1374–1427 increments the sequence, stores `requestIdAtSequence[sequence]`, snapshots `priceEscrowed=fee`, sets `listingId=0`, `Pending`, and distinguishes ETH versus token payment. Ordered processing at 1567–1605 rejects a missing/misordered sequence. Selection at 1683–1719 resolves a live slot to one listing ID and sets that ID on the acquisition before delivery. A failed delivery retains the selected token and payment escrow (`DeliveryPending`); `_finishAcquisition` decrements `unsettledAcquisitionCount` after processing (1624–1643). Balancer `_sync` at `PoolBalancer.sol` 605–626 reads the request ID by sequence and the acquisition's fee, listing ID and status, then credits keeper incentive only for `Fulfilled` status 2. **AcquisitionStatus** `DeliveryPending=7`, `DeliveryRefunded=8`; **ListingStatus** uses `DeliveryPending=6`, `DeliveryRefunded=7`. The probe asserted these distinct enum values.
3. **Curated refund recovery.** Balancer requires its item to be curated and pending, reads FWA's listing token/collection/status, requires listing status 7, deletes its local item, invokes FWA recovery, then sends the returned collection/token to the creator-selected recipient (`PoolBalancer.sol` 394–402). FWA `refundFailedDelivery` at 1746–1765 is purchaser-only after seven days; `recoverRefundedNFT` at 1767–1775 is owner-only and requires `DeliveryRefunded`. Its self-call `executeNFTDelivery` at 1777–1798 sends the **stored** collection/token to the owner and requires `liveNFTListing[collection][tokenId] == listingId` before clearing the controller. A wrong token from a different listing cannot be selected by this source path without a wrong stored tuple/controller or source-to-runtime divergence.
4. **Shape refund and ordinary withdrawal.** `recoverRefundedShape` (`PoolBalancer.sol` 589–603) likewise requires local Shape/PENDING and FWA listing status 7, asks FWA to return the listed token, then redeems the returned token ID at Shapes. `_withdrawAndRedeem` (782–795) reads each FWA listing's token ID, removes local active tracking, invokes `withdrawListingsTo(lids,this)`, then redeems those IDs. FWA `_withdrawListing` at 1000–1025 requires Active or unreserved Staged, `listing.depositor == msg.sender` and the exact `(collection,tokenId) → listingId` controller before `safeTransferFrom` of the stored token. Shapes `redeemBatch` and `_burnForRedemption` at 500–552 and 562–584 require each token to be owned by the caller, burn it, and send exact backing to the caller. A fabricated FWA token ID would normally cause an atomic revert if Balancer did not own that Shape; if Balancer happened to own another Shape with that ID, a wrong-token burn would require the FWA tuple/controller assumption itself to fail. No such state was observed or established as reachable here.

The FWA token-purchase variant does not arise through Balancer's exposed owner calls in this source: `configureTokenOffer` is FWA `onlyOwner` (1235–1245), while Balancer exposes no call to that selector, and `admissionStatus` rejects an enabled token offer. The tested acquisitions returned `tokenPayment=false`. This is a source-path constraint for this deployment, not a proof about future implementations or arbitrary corrupted pool state.

## Fork asset and authority ledger

The probe is [`identity-tuple.t.sol`](identity-tuple.t.sol), using local `ForkBase` creation against the pinned FWA factory/implementation, real Shapes and VRF router, and a test-only `FreezableNFT` collection. The collection's freeze flag was switched **after** the creator listed token ID 1, so FWA delivery to the buyer failed while custody remained at FWA. A second MockNFT collection had its own token ID 1 and listing ID. Balancer was the depositor and FWA pool owner throughout; the buyer had refund rights; the creator alone invoked curated recovery and unwind.

FWA owned all four; each listing's depositor was Balancer. The other collection's token ID 1 and both Shapes stayed with FWA. | FWA owner proceeds remained **0**. | After seven-day refund and curated recovery | Buyer called FWA refund; then creator unfroze and recovered only the frozen collection token ID 1. FWA returned it to Balancer, which transferred it to creator. The earlier mint fees were not redeemed. |

The second test used a separate fresh pool with one curated NFT and two Shapes. It bought two requests, delivered the **second** VRF word first so it waited `Ready`, then delivered the first word, whose FWA fast path settled the curated NFT. The later ready request could then be processed permissionlessly with caller-supplied gas. In the 10,000-gas sweep, no call at 200,000–800,000 committed; the first successful call at 810,000 delivered the Shape to the buyer (`AcquisitionStatus.Fulfilled=2`, `ListingStatus.Settled=4`). Balancer upkeep deleted that tracked Shape item, and `recoverRefundedShape` reverted `InvalidItem`. The failed calls did not change custody or entitlements. A saved exploratory trace, `identity-shape-gas.trace`, shows lower-budget executions reaching a successful Shape transfer but reverting at FWA's mandatory purchase notifier; no sampled call committed `DeliveryPending`. These nested calls share one Foundry test frame and access warmth, so **810,000 is not a universal transaction gas threshold**.

Final exit **0**: **2 passed, 0 failed**. Curated identity/recovery test gas **14,379,200**; ready-Shape gas-boundary test gas **27,643,371**. The exact final stdout is saved in [`identity-tuple.out`](identity-tuple.out). The exploratory `-vvvv` run was saved in `identity-shape-gas.trace` and exited 1 because its then-current assertion expected a Shape delivery failure; the trace instead showed fulfillment at the first successful 810,000-gas call. No chain transaction was broadcast and no production or existing test file was changed.

**Remaining open condition:** a genuine `DeliveryRefunded` Shape was not produced. The pinned Shapes `_update` at 1193–1200 rejects transfer to Shapes itself, and Balancer `canPurchase` rejects that purchaser; ordinary FWA-owned Shape `transferFrom` to another nonzero purchaser does not invoke a receiver hook. The sampled low-gas route did not cause a committed failure. These facts make a same-token-ID or self-custody counterexample unsupported in the inspected source and tested state, but do **not** prove Shape delivery cannot fail in every gas, dependency, or future-state condition. Accordingly, the `recoverRefundedShape` ignored-field assumption remains source-conditional rather than fork-executed. FWA and Shapes are only partially verified at Blockscout; the exact deployed source correspondence and any hostile runtime change remain limits to closing all four detector rows.
