The FWA source inspected exposes `StandardPool`'s ordered VRF request and settlement logic. A request increments `lastIssuedSequence`, records its sequence, fee escrow, purchaser and deadline, and asks its immutable VRF service/router for one word (`StandardPool.sol` 1374–1436). Only that router may call `rawFulfillRandomWords`; an on-time word is cached, and settlement advances only `nextSequenceToProcess`. Pending requests past their deadline, late words, empty inventory and out-of-tolerance price drift become purchaser refund credit (`StandardPool.sol` 1498–1680). A successful selection removes the listing from active totals, attempts `transferFrom` delivery in an isolated child call, and either accrues proceeds or leaves the NFT and payment in `DeliveryPending` (`StandardPool.sol` 1683–1719, 1777–1837). Anyone may retry delivery during seven days. Afterward, only the named purchaser can convert the purchase fee to refund credit; only the pool owner can recover the quarantined NFT afterward (`StandardPool.sol` 1736–1798). The separate VRF service fee is forwarded at acquisition and is not part of that purchaser refund (`StandardPool.sol` 1155–1166). These statements describe the inspected pool source; the router's Chainlink authentication and funding invariants need separate source/runtime review.

### FWA behavior used by Balancer

`createPool(0, expectedImplementation)` checks the factory's current implementation and clones it; the factory registers the clone before calling its `initialize(msg.sender)` (`PoolFactory.sol` 383–419). Balancer checks the implementation code hash, factory batch limit, returned `poolImplementation`, and pool `owner`, then installs itself as `purchaseOperator` and grants the pool Shapes operator approval (`PoolBalancer.sol` 239–256). FWA only lets the pool owner supply/withdraw/reprice inventory, withdraw owner proceeds, change local purchase settings or retire (`StandardPool.sol` 717–745, 965–1045, 1854–1859, 1999–2025). Its purchase-operator call is a fixed 100,000-gas `staticcall` on the *purchaser*, requiring a canonical ABI `true` (`StandardPool.sol` 1321–1346). It does not pass the payer; another address can pay for a named purchaser and that purchaser obtains NFT and refund rights.

The factory publishes `maxAcquisitionsPerTx = 5`, and the pool initializes its local batch maximum from factory config. The Balancer relies on one admitted batch per checkpoint: FWA advances `lastIssuedSequence` for each request, so the next `canPurchase` call sees a sequence mismatch. Pool mutation is locked while `unsettledAcquisitionCount > 0`, and only ordered processing decrements that count (`StandardPool.sol` 960–962, 1374–1430, 1569–1642). Balancer's `_requireIdle` and `_sync` use the same count before inventory changes/reconciliation. FWA's `listNFTs` accepts at most 20 per call; `withdrawListingsTo` accepts at most 20, checks depositor and sends using `safeTransferFrom` (`StandardPool.sol` 727–803, 985–1024). Balancer keeps its batch and unwind sizes within those limits.

**Economic mismatch requiring lead review:** On a successful ETH-paid delivery, FWA accrues only the request-time `basePrice` to `ownerProceeds`; `paid - basePrice` accrues to protocol fees (`StandardPool.sol` 1810–1829). `StandardPoolBuyback.payoutProtocolFees` sends the *entire* accrued protocol fee to `FWAV2Buyback` (lines 30–39). Balancer `_sync` computes `incentiveCredit` from the paid fee and the factory's 500 bps edge (`PoolBalancer.sol` 611–628), but this credit is a **cap on Balancer-funded keeper incentive**, not cash received by Balancer. The current `docs/SPEC.md` and `docs/OPERATIONS.md` describe it as spending FWA's edge. The ledger below shows the actual funding route. Whether Balancer's own markup and ETH reserves make the authorized keeper policy economically acceptable is a separate economic decision; this slice did not model it over purchase/refund sequences.

## Shapes and ENS behavior

`Shapes.mintBatch` requires exact `quantity × (denomination + current mintFee)` payment, increments redeemable backing, credits fees to a separate fee liability, then `_safeMint`s consecutive token IDs to `msg.sender` (`Shapes.sol` 370–465). Thus Balancer's `onERC721Received` is reached on mint, and its hook is pure and returns the selector. `redeemBatch` requires `msg.sender` to own each token, burns them, reduces redeemable backing, then calls the recipient (`msg.sender`) with the exact sum (`Shapes.sol` 500–552, 562–590). The fee is not returned. Shapes rejects transfers to itself in `_update` (`Shapes.sol` 1193–1200), matching Balancer's purchaser exclusion. A Shapes approval to the FWA pool is economically broad: the approved pool can transfer/redeem any Shape the Balancer holds, though the inspected FWA inventory methods require its owner and take only enumerated listings. Balancer's permanently held approval should be treated as an authority edge, not merely a convenience.

ENS `owner(addr.reverse)` selects a registrar dynamically. The pinned registrar's `setName` acts on `msg.sender`'s reverse node and calls its default resolver (`ReverseRegistrar.sol` 675–735). Balancer calls this only from creator-only `setENSName`/`clearENSName`; it does not validate a forward address record. A registry ownership or registrar change can change the external code reached by later creator calls. The fork probe exercised the observed registrar and resolver but cannot establish future behavior.

## Open integration questions for the lead

1. **INT-1, keeper economics:** Decide whether the design accepts paying incentives from Balancer ETH while the calculated edge is routed entirely to FWAV2Buyback. Deciding evidence is a purchase/refund/keeper sequence ledger with owner net cash and reserve before/after; this slice did not run that economic sequence.
2. **INT-2, VRF and notifier dependency:** Independently inspect the pinned VRF service/router and `PoolPurchaseNotifier` verified source and runtime correspondence, including their callback/fee behavior. This review covered the inherited pool's request, cache, FIFO settlement and refund code, but not the service's Chainlink authentication or notifier's downstream calls.
3. **INT-3, future authority drift:** The implementation code hash is pinned for new Balancers; factory global controls, the ENS `addr.reverse` owner, Shapes fee recipient/admin and existing FWA pool configuration remain external authority. Evaluate the specific deployment/release policy for these changes. The pinned fork values alone establish no future behavior.

No fixes, broadcasting, or external writes were performed. The known open paths require supported continue/stop dispositions in the lead's run record before an overall audit conclusion.
