## Router behavior relevant to Balancer

1. **Request authority and funding.** The FWA pool calls `prepareRequests` with exactly the service fee times request count. The router requires an active, unpaused subscription, a registered and consumer-ready pool, matching request tuple/config, request-cap headroom and enough ETH to restore `minimumSubscriptionBuffer + (prepared + coordinator outstanding) × maxFulfillmentCostWei` (`FWACloneVRFService.sol` 257–280, 376–465, 770–798). Each subsequent `requestRandomWords` consumes one prepared credit and makes the real Chainlink request using the router's approved key, subscription, confirmations, 1.5 million callback gas and native payment. It records the returned request ID against the original pool before returning. Failure rolls the entire FWA purchase transaction back. Balancer has no authority to choose the router, change its tuple or withdraw its funds.
2. **Callback authentication and delivery.** The imported Chainlink base's `rawFulfillRandomWords` requires `msg.sender == s_vrfCoordinator` before the router's internal callback (`VRFConsumerBaseV2Plus.sol` 143–147). The router accepts only a recorded outstanding request, releases its coordinator liability, stores the first word (or an empty-array marker), and then tries a bounded call to the original pool (`FWACloneVRFService.sol` 475–537). Pool `rawFulfillRandomWords` in turn requires `msg.sender == vrfService` (`StandardPool.sol` 1498–1501). The router retains 80,000 gas after its 1.2 million pool stipend; if insufficient gas remains it defers delivery. A pool-call failure leaves the word stored and permits anyone to call `deliverRandomness(requestId)` later. The stored word is not replaced or re-requested. This isolates the Chainlink callback from pool failure, but depends on the real coordinator's proof verification, which was not separately reviewed here.
3. **Timeout and refunds.** FWA's pool caches on-time words and settles only the canonical sequence. A late or missing word can be processed as an expired local request after the pool's deadline, making the **named purchaser**, not payer or Balancer, holder of the acquisition-fee refund credit. The separate router/VRF fee is spent and is not refunded by the pool. The router can permissionlessly mark a coordinator callback lost only when the coordinator's request commitment getter returns zero; this releases service coverage liability but does not generate replacement randomness (`FWACloneVRFService.sol` 539–579). Pool local expiry does not by itself release the router's outstanding liability. This can eventually exhaust the router's per-pool/global request caps or coverage if coordinator requests remain unresolved, even when Balancer has reconciled and reopened its own checkpoint. Existing FWA expiry/refund processing remains available.
4. **Processing liveness.** `FWACloneVRFService.processAcquisitions(pool,maxCount)` is an optional factory-approved operator route paid from subscription-safe liquid surplus; it can revert if no surplus/reimbursement is available. The underlying FWA pool `processAcquisitions(maxCount)` remains permissionless and does not depend on that sponsorship (`FWACloneVRFService.sol` 585–632; `StandardPool.sol` 1567–1607). Factory pauses and subscription termination bar *new* requests; the inspected router/pool paths leave stored-word delivery and pool processing callable. This is source-based; no adversarial long-running coordinator outage was executed in this slice.
5. **Governance surface.** Factory-only router settings can pause requests, change limits and fee/coverage policy, and rotate to a fresh VRF gas lane under paused/no-outstanding conditions (`FWACloneVRFService.sol` 638–798). The Chainlink base allows its `setCoordinator` from either its owner or current coordinator; source comments state the factory provides no generic wrapper, while an official coordinator migration path remains. These external authority changes may stop new FWA purchases or alter VRF cost and callback timing without changing the pinned Balancer implementation. Balancer's admission hook does not need to predict them because FWA's purchase path checks the current factory and router gates, but Balancer operation may pause.

## Purchase notifier and collection callback

`StandardPool` calls the immutable notifier after a fulfilled acquisition's state and accounting are committed in the processor frame. Its call gives the notifier 300,000 gas, and a failure **reverts that processor attempt** (`StandardPool.sol` 1597–1605, 1839–1847). The notifier requires at least 290,000 gas at entry; it verifies the calling pool is registered, uses the exact implementation and notifier, and has a `Settled` listing and `Fulfilled` acquisition that agree on listing ID and purchaser (`PoolPurchaseNotifier.sol` 89–117). These admission checks are mandatory, not best-effort. An undergassed processor attempt can therefore revert without advancing FWA's queue. Retrying with sufficient gas remains possible; the original VRF word is cached.

Only the **NFT collection** is a callback receiver. The notifier first probes ERC-165 under 30,000 gas; a rich `IPoolPurchaseCallback` receiver gets one 100,000-gas call with pool, purchaser, successful settlement caller (`resolver`), token, paid amount, listing price and random word. The resolver can be the pool itself during the VRF fast path; it is not necessarily the payer. Otherwise a legacy `IFWAPurchaseCallback` receiver may get one 100,000-gas call for ETH-paid purchases. The notifier ignores receiver success/failure and does not copy return data (`PoolPurchaseNotifier.sol` 119–197). Thus a malicious curated collection can execute code during settlement, but its own callback failure is isolated. Shapes' inspected `supportsInterface` implementation does not list either purchase callback interface, so the notifier should only probe it, not call a purchase receiver on Shapes; this last conclusion is source/interface based, not a targeted fork trace of the notifier.

The collection callback occurs **after** FWA has accrued base-price `ownerProceeds`, decremented `unsettledAcquisitionCount`, advanced the processing sequence, and marked the acquisition fulfilled, while FWA's `processAcquisitions` reentrancy lock is still held. A hostile collection can call Balancer's public functions. Balancer `canPurchase` sees the issued-sequence/checkpoint mismatch. Balancer's `performUpkeep` and `collectProceeds` are themselves `nonReentrant`; if invoked from this callback for an ETH-paid delivery, their attempt to pull the freshly accrued FWA proceeds reaches FWA's locked `withdrawOwnerProceeds` and reverts, and the notifier isolates that callback failure. If the collection is also the Balancer creator, its unguarded creator-only config/role methods remain reachable; that role alignment is creator-chosen. This analysis covers the specified call ordering and guards, not every arbitrary collection behavior.
