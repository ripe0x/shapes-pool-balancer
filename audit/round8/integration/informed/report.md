# Round 8 integration informed pass

Target production revision: `2ac7a7e7b965d1798729068566c026128a4ba4b9`. This is an independent assessment of the keeper, planner, dashboard and deploy script against real mainnet forks at blocks `26382349` and `26399837`. No production or existing-test files were edited, no mainnet transaction was broadcast, and no protocol contract was mocked or given a fake balance/state. Initial and supplemental discovery seals remain unchanged (`d2c9b07a9644552565cc614b4a131c8b574b3cae1fdfae6490f83b5353f54e39`, `42c3fc2228536a4e55cfea13bca64daca00bcb361f09cc501e0e00d1ba958eab`).

## Findings and limits

### 1. Dashboard upkeep simulation has the wrong caller and no bid price

`app/src/App.tsx:63-64` simulates `performUpkeep` with `account: b`, the Balancer contract address. `App.tsx:88,191-209,337-349,371-375` turns that boolean into the pool status and conditional Run upkeep action shown to the creator. `PoolBalancer.sol:562-563` always permits the creator but rejects an unapproved caller when the factory restricts keepers. The real-fork `testRestrictedKeeperListStillLetsCreatorStock` shows `canKeep(balancer)==false`, `canKeep(keeper)==false`, and successful creator upkeep under restriction. In admission status 0, the dashboard can say “Nothing needs attention” and hide the secondary upkeep button although creator upkeep can reconcile work. Statuses 2 and 6 show Run upkeep regardless of this boolean, so this is bounded to states whose button depends on `d.upkeep.needed`. This UI conclusion is source inference, not a screenshot of a creator wallet. `App.tsx:475-477` correctly simulates with `account: me` in the design/save flow.

Separately, `app/src/tx.ts:15-23` supplies no `gasPrice`, `maxFeePerGas`, or `maxPriorityFeePerGas` to `simulateContract` or `estimateContractGas`; `App.tsx:126-132` uses this for every dashboard write. `App.tsx:63,475-476` similarly omits price for upkeep probes. Tenderly `eth_call` to the real FWA VRF service's `requestFee()` returned 0 at both pinned and recent blocks when gas price was omitted; explicit 1 gwei returned 0.00013561352298 ETH and 0.00173128793292 ETH respectively, while explicit EIP-1559 fields returned 0.00025261352298 and 0.00184828793292 ETH. The actual request fee is bid-dependent, so a zero-price result is not a reliable transaction quote. Fork test `testGasPriceZeroSimulationDiffersFromBid` sets the recorded block basefee, then proves the same 0.0117 ETH funded pool lists one Shape at zero `tx.gasprice` but reverts `NoUpkeepNeeded` at a 1 gwei bid after snapshot restoration. This is a concrete possible simulation/estimate versus inclusion discrepancy near the liquidity boundary; it does not prove a user transaction failed on mainnet. The keeper bot supplies explicit EIP-1559 fields at `keeper/keeper.ts:185-187,214-218`, so this branch is dashboard-specific. Existing `app/src/tx.test.ts` asserts absence of fee fields; it is not evidence that the behavior is safe.

### 2. Existing curated listings are repriced only in the planner

`shared/planner.ts:110-118,162-181` computes curated prices from each base and the **current** markup. `App.tsx:1027-1041,1104-1108` supplies listed NFT bases and current markup to the economics view. `PoolBalancer.sol:304-323` changes markup for future listings but does not reprice listings already on FWA. A real-fork BAYC #1 fixture was listed at 0.02 ETH, then markup changed to 1000 bps. Its live FWA acquisition fee was 0.018260977630488814 ETH; recomputing from all three actual listing prices (`0.02`, `0.012245`, `0.02449` ETH) matched exactly. Planner evaluation returned 0.018755188418609791 ETH, overstating by 0.000494210788120977 ETH (about 2.7%). This affects estimates and displayed creator economics for previously listed curated NFTs after a markup change; contract fees and transfers are unaffected. The app notes that listed prizes retain their price at `App.tsx:698-700,883`, which does not correct this calculation.

### 3. Keeper can persist indefinitely at replacement cap

`keeper/keeper.ts:92-105` reloads/saves pending transactions. `:222-249` clears pending only when one saved hash has a receipt or the latest confirmed nonce exceeds the pending nonce. If all saved hashes are evicted or unavailable, the nonce remains unconsumed, and five replacements have already been sent, `:251` returns true on every tick forever. `:173-175` therefore never attempts fresh upkeep for that Balancer; restart preserves the same state. A reorg that removes the last receipt can put the transaction back in this branch; if a later old hash mines or the nonce is consumed, the branch recovers. `health()` at `:285-301` can still return HTTP 200 because the tick completes and the pending address appears only in JSON. Under a restricted keeper list with only this keeper, this can leave reconciliation/restocking to the creator. This is a source-proven conditional liveness issue; **the network prerequisite (all six same-nonce transactions dropped with none later mined) was not reproduced on a real fork**. Existing `keeper/e2e.ts:160-178` exercises a replacement that mines, not exhaustion.

### 4. Full-history dashboard event reads fail closed for the view

`App.tsx:65-66,98` fetches all `ItemDrawn` logs from `FROM_BLOCK` on every 15-second refresh, with no chunking or fallback. The failed-delivery IDs are deduplicated at `:69` and checked against current item state at `:82`, so ordinary duplicate/reorged-out events are removed after a successful reload. A range-limit or transient `getLogs` failure rejects the entire load, and `PoolView:338-341` replaces the pool UI with an error even if direct Balancer reads work. `App.tsx:231-246` similarly full-scans `BalancerCreated` for each wallet connection and silently leaves loading state on an RPC failure; it does not deduplicate returned addresses. `FROM_BLOCK` defaults to zero (`app/src/chain.ts:20`) and deployment configuration must supply the right block. These are source-traced operational risks; no provider range-limit failure was forced. Asynchronous wallet-change and refresh calls also have no cancellation, so an older response can overwrite newer UI state; this was not reproduced in a preview.

The keeper's event path is more bounded: `keeper/keeper.ts:117-145` chunks factory logs at 10,000 blocks, overlaps 64 blocks, deduplicates Balancer addresses, and removes a reorged-out creation when its code is absent. Its persisted `lastScanned` means a reorg deeper than 64 blocks or a wrong `FROM_BLOCK` can leave missed creations until state is reset. Existing `keeper/e2e.ts:151-196` covers restart and a shallow creation reorg, but was not rerun here because it writes a root deployment file and funds a protocol coordinator account.

### 5. A keeper restock can invalidate a pending player quote

The focused real-FWA fork race in `RaceFork.t.sol` first settled a Shape draw from a pool with five Shape prizes and one real BAYC. The Balancer still admitted purchases at that point. A second buyer took a quote, then a keeper restocked the lost Shape at a 5 gwei basefee. At pinned block 26382349, FWA inventory version moved **2→3** and fee **0.013989614775735308→0.014477479443579256 ETH** (increase 0.000487864667843948 ETH, 3.49%). At recent block 26399837, version moved **2→3** and fee **0.014590782023240358→0.015010848656261784 ETH** (increase 0.000420066539021426 ETH, 2.88%). With the old version and fresh fee, real FWA reverted `InventoryVersionMismatch(2,3)`. With the new version and old maximum fee, it reverted `AcquisitionFeeTooHigh()`. Both failed calls left the buyer's ETH balance unchanged in the Foundry transaction simulation, and a retry with fresh guards succeeded. This proves the version/price race and refund of call value on revert; it does not measure real-wallet gas expenditure or a population revert rate. A timing model in which the buyer waits across exactly this one restock yields 2 of 2 stale-guard attempts rejected, but this sample is not an estimate of normal traffic.

### 6. Receipt event provenance is weak but not reachable from the pinned upkeep path

`keeper/keeper.ts:230-236` decodes every receipt log and accepts any matching `KeeperPaid` event without checking `l.address === b`; a matching third-party log could poison its `earnedWei` and audit P&L (not the on-chain reward). For the current pinned `performUpkeep` path (`PoolBalancer.sol:562-595,650-721`), the external calls are FWA acquisition/proceeds reads, Shapes/Pack mint, FWA listing of those fixed assets, and ETH payout to this bot's own EOA. No curated collection is called during upkeep. With the pinned integrations and EOA keeper, an attacker-controlled matching emitter was not reached, so this is a dormant provenance weakness, not a demonstrated exploitable finding. A future callback-capable integration or contract keeper would require re-evaluation.

### 7. Bounded estimate-to-inclusion measurements and keeper admission cap

`gas_delta.ts` used the exact `Deploy.s.sol` path on a private Anvil fork of Tenderly block 26382349, then created a pool and configured five 0.01 ETH Shapes. It took 24 independent snapshots of this opening upkeep state. For each, it mined 1–24 blocks, called the local node's `eth_estimateGas`, mined one more block, and sent the same upkeep with a 30% gas limit margin. All 24 local-fork receipts succeeded. Estimates ranged 3,281,364–3,281,532 gas; billed receipts ranged 3,205,630–3,205,795 gas. Receipt minus estimate ranged **−75,835 to −75,630 gas**, so no positive growth was observed in this exact five-Shape opening path. The samples did not include reconciliations, mixed denominations, packs, competing draws or same-block fulfillment, and they do not explain the prior 3-of-340 rehearsal failures. The local node was stopped after the run; no mainnet transaction was broadcast.

The bundled keeper's `decide()` first rejects any estimate above 3,200,000 (`keeper/keeper.ts:37-40`), even though the contract caps **rewarded measured gas**, not pre-refund estimate (`PoolBalancer.sol:711-721`). On the observed 3,281,532 estimate, an explicit policy call returned `{send:false, reason:"estimate above reimbursable maximum"}` at pinned basefee 57,954,497 wei, default priority 50,000,000 wei, maximum plausible reward 845,454,390,400,000 wei and default loss allowance 0.0002 ETH. A 1 ETH loss-allowance override returned the same result. Thus this exact opening batch would be skipped by the bot; creator/manual upkeep can still perform it. The balanced board starts with 24 small Shapes (`shared/design.ts:51`), and `_fillDeficit` starts from the smallest size (`PoolBalancer.sol:659-675`), so its first batch has the same prize type, but its actual curated-inventory gas was not measured. A possible remedy is to separate the bot's *estimate admission ceiling* from the contract's *rewarded gas cap*, subject to the owner's tolerated keeper loss and liveness goal.

`draw_delta.ts` used a second private Anvil fork with real BAYC #1, FWA, Shapes and Packs. The player quoted at a 1 gwei bid: FWA acquisition fee 0.013769246329024965 ETH, VRF fee 0.00234 ETH, total 0.016109246329024965 ETH; `eth_estimateGas` was 644,677. The inclusion bid was raised to 3 gwei. The acquisition fee stayed the same, while the VRF fee rose to 0.00702 ETH and total to 0.020789246329024965 ETH. Sending the stale value with 30% gas margin produced a **reverted receipt of 110,620 gas** with `InsufficientPayment()` selector `0xcd1c8867` (`cast sig 'InsufficientPayment()'` matched). The wallet lost exactly `gasUsed × effectiveGasPrice` and no call value. A fresh quote and retry succeeded: estimate 644,677, billed 584,638 gas. This is one price-change timing case and does not provide a player revert frequency or largest possible gas growth. No coordinator delivery was needed because the draw is left pending.

### 8. Secondary off-chain prompts S1/S2/S3

- **S1/S2 wallet switch:** `prepareWrite` preserves the simulation's account and chain in its result (`app/src/tx.ts:15-23`), and `useTx` passes the connected address for each write (`App.tsx:126-132`). The existing `app/src/tx.test.ts:58-81` uses a fabricated wallet/client to assert wagmi refuses a different account or chain; that test is not a real wallet interaction and was not rerun. `App.tsx:231-246` has an uncancelled async `loadMine` request across account changes, so an old response can overwrite the newer account's pool list; `:236-237` selection filtering applies only to each response's captured account. These are source dispositions; actual wallet-switch UI behavior remains **unresolved without a preview interaction**.
- **S3 failed page approval:** `App.tsx:1243-1257` calls `tx.send('Approve pool page', ...)` and returns before the FWA HTTP POST if it is false. `useTx.send` returns false on write or receipt failure (`App.tsx:138-163`). Source therefore shows a failed approval does not intentionally publish the page. No rejected wallet transaction was exercised in a preview; that interaction remains untested.

- Live FWA factory at both sampled blocks: implementation `0x85Faf92967705dc45535eBCA74D6333F6bCBfEe7` with expected codehash, edge 500 bps, max acquisitions 5, max staged listings 0, purchases enabled, VRF requests unpaused, global withdraw-only false. Shapes mint fee 0.001 ETH. `shared/planner.ts:6-22`, `keeper/keeper.ts:20-22,80-81,166-170`, and `src/PoolBalancer.sol:45-98` agree on batch 5, Shape-unit restock 5, 3.2M measured-gas cap, 5 gwei cap, 0.05 gwei priority, and restock fee of 900k gas plus 0.0002 ETH. `docs/GAS.md:161` alone says **6** Shape units per call; `docs/GAS.md:175` and the code say **5**. This is documentation drift, not a runtime mismatch.
- In the real FWA purchase trace (`audit/round8/integration/fulfillment_attempt.output:275-300`), pool VRF callback gas is 1.2M and the service forwards 1.5M to the coordinator. The app intentionally excludes the VRF fee from the design price (`App.tsx:878`), but no fixed 1.1M service-gas assumption was found in this target's source, planner or keeper. The service fee is gas-price dependent as measured above.
- `script/Deploy.s.sol:35-39` checks chain, FWA implementation and codehash, and max acquisitions 5. `PoolBalancer.initialize` checks both acquisitions 5 and staged listings 0 at `PoolBalancer.sol:265`. The script postflight `Deploy.s.sol:51-59` checks factory wiring/keeper admin, implementation lock and dependencies, Packs backing/minimum, and deployed code. It does not assert FWA pause or `maxStagedListings` preflight, but the live values passed. A dry-run of the **exact script** on a Tenderly fork passed without `--broadcast`, and its `vm.writeJson` target was isolated to `informed/project/deployments/1.json`. The dry-run did not create a Balancer clone or exercise a draw; the independent fork tests in the sealed supplement cover those paths.
