## Security findings, ranked by consequence

### C-S1. PR 29 cross-tab reservation can be erased by the wrong tab — high, executed storage transition; ETH consequence reasoned

`app/src/App.tsx` uses `Date.now()` as the sole reservation identity. Two tabs can read the same empty `transferKey` before either writes and receive the same millisecond timestamp. Tab A reserves; Tab B reserves and saves a pending hash; A's wallet rejects and calls `releasePending(key, since)`. The helper checks only that timestamp, so A deletes B's record. The next same-contract ETH transfer sees no pending record while B's transfer may remain pending. [The exact repair helper witness](app-cross-tab-release.mjs) ran in two VM contexts against Node's native Web Storage: B's hash was present before A's error and absent afterward; [output](app-cross-tab-release.log) records exit **0**. This is an executed storage transition, **not** a real two-wallet or two-ETH transfer. No successful RPC or protocol answer was fabricated. Scheduling likelihood is unmeasured.

At the A launch example of **5 ETH per contribution**, a second 5 ETH send would add **5 ETH** unintended pool capital under R73; the creator may claim available surplus. The money consequence follows from A's two real-transfer fork witnesses and the candidate's payable contribution rule, not from a repaired-chain transaction in this probe. **Smallest fix:** use a collision-resistant identifier per attempt, remove only the record owned by that attempt, and make cross-tab reservation acquisition atomic so both empty reads cannot open wallets. [Witness report](app-repair-witness.md) gives exact command, assumptions and limitations. This is a **new failure of the repair**; further re-attacks stopped here.

- A millisecond timestamp is treated as proof of reservation ownership across tabs, while localStorage acquisition is a separate read and write. A failed wallet in one tab can erase another tab's pending transfer.
- The repaired guard releases a hashless, nonce-less record after **24 hours** even though an unseen higher-nonce transaction can remain mineable; this was source-reviewed only because the first repair break stopped testing.
- The keeper's endpoint check asks the configured endpoint for its chain ID before deciding whether that endpoint is permitted. This may be unavoidable for local forks, but it is not an independent identity check.
