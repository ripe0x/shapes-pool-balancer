# External-call asset and authority ledger (discovery draft)

Target: `0f017843ec333f499809f751e19017be325448e3`. This ledger groups identical call sites reached by several paths. `B` is the Balancer, `P` its FWA pool, `S` Shapes, `C` the creator, `R` a creator-chosen recipient. It tracks *different NFT identities*; a listing ID is not itself a token ID. The Solidity transaction reverts atomically if an uncaught external call reverts. The initial table was prepared during discovery; the integration source and hostile fork amendments below are informed evidence, not blind-discovery additions.

## Callback dispatch and guard state

During a guarded entry (`listCurated`, `listCuratedBatch`, `updateCuratedPrice`, `withdrawCurated`, `recoverCuratedNFT`, `recoverUntrackedNFT`, `collectProceeds`, `claimSurplus`, `unwind`, `performUpkeep`, `recoverRefundedShape`), Solady's guard slot equals the Balancer address. A nested call to any of those entries reverts `Reentrancy()`. The following unguarded public entries remain callable in a state-changing callback: `depositETH`, payable `receive`, `transferCreator`, `acceptCreator`, `configure`, `open`, `close`, `retire`, `setENSName`, `clearENSName`, `approvePoolPage`, `revokePoolPages`, `initialize` (but it reverts after initialization), and `onERC721Received`. The creator-only subset succeeds only if the callback caller is the then-current creator; `acceptCreator` instead requires the current `pendingCreator`. Getters, `admissionStatus`, `canPurchase`, `withdrawableSurplus`, `requiredReserve`, `getPlans`, `getActiveIds`, `getActiveShapes`, `denominationAmount` and `isValidSignature` remain readable, including through callbacks. During `STATICCALL` to a view target, any nested state-changing operation reverts in the static context even if the target is hostile. This dispatch list does not assert that every fixed dependency actually makes a callback.

## Calls with asset or authority effects

| Call sites | Before → during → after; callback authority |
| --- | --- |
| `initialize`: FWA `createPool`, `poolImplementation`, `owner`, `setPurchaseOperator`; Shapes `setApprovalForAll` (245–253) | Before: `creator` set, ETH deposit remains at B, no pool or Shape approval. During: FWA factory creates P with B as owner; P's implementation and owner are checked; B is installed as purchase operator; S grants P operator authority over **all Shapes held by B**. After: P and S approval are fixed in B storage. The factory and P call as themselves, not as C; `initialize` cannot be called again. Need verify factory's own callback and proxy behavior. |
| `open`/`close`: P `setBool` (308, 316) | Before: `enabled` and checkpoint state determine local admission. During: P's acquisitions-enabled flag changes; `close` invalidates checkpoint before the call. After: P's flag and B's local flag should agree if call succeeds; any revert rolls back both. P callback sender is P; creator-only callbacks are unavailable unless C=P, which must be ruled out. |
| `listCurated`/batch: collection `transferFrom`, `ownerOf`, `approve`, then P `listNFT`/`listNFTs` (340, 359, 961–963) | Before: C owns each specific token, B holds none; checkpoint invalidated and creator work marked before the first call. During: each token moves C→B, B grants P token approval, then P pulls B→P and records price/weight/listing ID. In a batch, B temporarily holds earlier tokens while later collection calls run. After: each recorded active listing should identify exactly the token at P; B no longer owns it, active IDs/totals updated. An arbitrary curated collection can callback as itself; if C is that collection, unguarded creator entries are reachable while the guard is set. Guarded recovery/withdrawal are not. P callback capability requires verified source review. |
| `updateCuratedPrice`/`_reprice`: P `updatePrice` (373, 736) | Before: P and B store old listing price; admission invalidated by creator update or already invalid during upkeep. During: P changes one active listing's price and version; B's `it.price` is still old until return. After: B writes new price. A revert restores both. Callback read paths could observe this transient mismatch; guarded mutators revert, but creator-only unguarded paths need reachability analysis. |
| `withdrawCurated`: P `withdrawListingTo` (388) | Before: active curated token owned by P; B removes ID and invalidates checkpoint. During: P sends that **specific token** to R. After: P no longer lists it; R should own it; B has no item record. R is supplied by C. Hostile NFT transfer behavior may revert and prevent this withdrawal; verify. |
| `recoverCuratedNFT`: P `recoverRefundedNFT`, collection `safeTransferFrom` (397–401) | Before: the pending item is at P with `L_DELIVERY_REFUNDED`; no live listing. During: B deletes the record, P returns that token P→B, then B sends B→R. After: R owns it, B has no item record. If the collection or R rejects, the whole recovery reverts and P retains the token/status. Both transfer and receiver hooks may callback under the guard. |
| `recoverUntrackedNFT`: collection `ownerOf`, `safeTransferFrom` (414–415) | Before: B must be reported owner of the named token; P and FWA factory addresses are excluded as collection targets. During: collection transfers the named token B→R. After: R should own it. This function does not consult tracked IDs, relying on the invariant that tracked NFTs are never held at B between transactions; guarded reentry cannot invoke it mid-transfer. A malicious collection can lie about `ownerOf`, but its own NFT rights are at issue unless it can impersonate another collection. |
| `_collect`: P `ownerProceeds`, `withdrawOwnerProceeds` (947–948) | Before: P owes settled proceeds to B; B ETH excludes them. During: P sends proceeds to B's payable `receive`. After: P debt falls and B liquid ETH rises; no keeper payment from `collectProceeds`. Need verify P's withdrawal rules and that the amount returned equals ETH received. |
| `claimSurplus`: `_collect`, `safeTransferETH` (436–443) | Before: if open, FWA idle/reconciled; B holds liquid ETH and may be owed proceeds. During: proceeds enter B, `requiredReserve()` is read, then B transfers at most balance−reserve to R. After: B balance should remain ≥ reserve, assuming no callback changes the reserve between calculation and transfer. Guarded mutators cannot reenter; if R=C, unguarded creator config/open/close/role transitions can run in the ETH receiver callback **after** the amount is chosen. Investigate whether this changes the effective requirement mid-call. |
| `_withdrawAndRedeem`: P `listings`, `withdrawListingsTo`; S `redeemBatch` (788–794), used by `unwind` and rebalance | Before: each named Shape token is owned/listed by P and counted active; B preemptively removes tracking. During: P transfers exact token IDs P→B, then S burns those IDs and returns exact backing to B. After: IDs no longer exist and B liquid ETH rises by backing, less no additional fee. Fixed S/P behavior and batch bounds need verification. Reverts roll back tracking. |
| `_fillDeficit`: S `mintBatch{value:cost}`, P `listNFTs` (815, 826) | Before: B holds cost as liquid ETH; no managed Shape for each missing ID. During: B sends cost = `need × (backing + mintFee)` to S; S mints sequential IDs to B through its ERC721 receiver; B's standing approval lets P pull them into listings. After: P owns the newly minted token IDs, B has no managed Shape in custody, and B tracks returned listing IDs/prices/denominations. Between mint and P listing, B temporarily owns Shapes while `activeShapes` still reflects the old set; guarded mutators cannot reenter. S's actual `_safeMint` callback is B's pure receiver. Need verify sequential ID and failure behavior. |
| `recoverRefundedShape`: P `listings`, `recoverRefundedNFT`; S `redeemBatch`; `_payKeeper` (594–602) | Before: one pending Shape token is owned by P and delivery-refunded; B has its item record. During: B deletes record, P sends token P→B, S burns it and pays backing to B, then B rewards caller. After: pending record gone, token burned, B has backing minus reward; recipient of reward is `msg.sender`. A revert rolls back all. |
| `_payKeeper`: Solady `forceSafeTransferETH` (843–862) | Before: B holds liquid ETH; measured gas and `incentiveCredit`/`creatorWork` determine a capped amount. During: B sends at most its balance to `msg.sender` using ordinary call or forced transfer if receiver rejects. After: keeper has payout, B loses same ETH, `incentiveCredit` may fall; event follows transfer. A keeper callback is under the guard, but if keeper=C it can invoke unguarded creator entries before `performUpkeep`'s final `creatorWork` update. The force-send path may avoid a callback when receiver rejects. |
| `retire`: P `retirePool` (469) | Before: B locally closed. During: B as P owner marks P retired. After: permanent P state change; listed assets still require P withdrawal/recovery methods. No ETH or NFT immediately moves. Verify fixed implementation keeps exit methods usable. |
| ENS: `ENS.owner(addr.reverse)`, registrar `setName` (479, 484) | Before: C chooses a name, B owns its reverse authority only as recognized by the current registrar. During: B calls registry owner then registrar, which receives B as sender and may write B's reverse record. After: B emits the requested name, but does not verify registrar output or forward resolution. No B asset approval or ETH transfer. A malicious registrar could callback as itself; creator-only calls require it also be C. |

## Read-only external calls and pure libraries

The remaining inventory call sites are views of P (`unsettledAcquisitionCount`, sequences, acquisitions, listings, totals, inventory version, purchase state, acquisition fee, proceeds, owner, retired), FWA factory (`edgeBps`, `maxAcquisitionsPerTx`, `globalWithdrawOnly`, `poolImplementation`), S (`denominationAt`, `mintFee`, `ownerOf`), ENS (`owner`), or pure Solady string/hash helpers. Before/during/after each such `STATICCALL`, balances, token ownership, approvals and authority are unchanged in the EVM. A failing or gas-burning target can revert or exhaust a higher-level action, so liveness and the 100k admission budget still require separate tests. The `canPurchase` path makes several external views while FWA provides a 100k stipend. This ledger does not count static calls as proof that returned values are honest; fixed dependency source/fork checks must establish the relevant semantics.

## Integration calls initiated outside the Balancer

Players call P's acquisition functions directly. P then calls B's `canPurchase(purchaser)` under a 100k static stipend, may issue VRF requests, settle draws, deliver an NFT to the purchaser or refund after failure. These transfers and entitlements are not controlled by the Balancer after admission. Verify exact P/VRF rules separately, especially the sequence/version advance, batch size, escrow/proceeds and delivery/refund status codes. No claim that player exit is independent is accepted from this ledger alone.

## Informed external-state and callback amendment

| Integrated call/state change | Before → during → after; authority and guard |
| --- | --- |
| FWA `acquireBatch` → Balancer `canPurchase` → VRF router `prepareRequests` | Before: FWA has active inventory totals and Balancer may have a valid checkpoint; payer owns ETH and may choose a separate purchaser. During: FWA's 100k staticcall asks only about the purchaser; Balancer cannot mutate in that context. FWA forwards the nonrefundable service fee to the fixed router, escrows the acquisition fee, and issues up to five requests. After: sequence advances and Balancer admission closes; if router coverage fails, the whole purchase reverts and neither fee is spent. Router coverage is not checked by Balancer, so an expired local batch can leave Balancer status 0 while router coordinator liabilities reject a next request. |
| VRF callback / FWA settlement / notifier | Before: FWA holds acquisition escrow and listed NFT, router holds an outstanding coordinator liability. During: authenticated coordinator response reaches router and then FWA; FWA settles ordered requests. Successful transfer moves NFT P→purchaser, credits base price to owner proceeds and the full edge to protocol buyback. Failed transfer retains NFT at P and creates `DeliveryPending`; after seven days purchaser can claim acquisition-fee refund, with VRF fee excluded. The notifier then may call a hostile curated collection within a bounded stipend after FWA accounting is committed; it ignores collection callback failure. After: Balancer's sequence is stale until upkeep. A collection callback can reach unguarded creator entries only when the collection itself has creator/pending-creator authority; guarded asset entries and FWA locked owner-proceeds withdrawal revert if reentered during settlement. See `audit/integrations/informed.md` for source bounds. |
| Hostile collection `seize` outside Balancer/FWA | Before: P owns a listed token and FWA counts its weight; Balancer tracks its listing and has an admitting checkpoint. During: an outsider invokes a malicious collection's public out-of-band `_transfer(P,stranger,tokenId)`. Neither P nor Balancer receives a callback or state notification. After: stranger owns the token, while P's active listing/totals and Balancer's checkpoint still match each other. `canPurchase` remains true; if FWA later selects that listing, delivery fails and purchaser obtains a delayed acquisition-fee refund. This is the concrete conditional F1 path; no EVM-level custody check can force an arbitrary collection to report or preserve honest ownership. |
